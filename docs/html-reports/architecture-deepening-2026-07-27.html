A. Collapse the transition-error flow into a useTransition hook

Strong in-process
src/App.tsxsrc/lib/transitions.tssrc/components/StoryDetail.tsxsrc/components/TerminalView.tsxsrc/components/Board.tsx

Before

    TV[TerminalView] -->|onReactivate| App
    App -->|setTransitionError| Toast[Error Toast]
    App -->|performTransition| Runner[TransitionRunner]

App.tsx is a pass-through: it receives transition calls, delegates to the Runner, then sets error state for a toast. Two callers thread through one shallow orchestrator.

After

graph TD
    Hook[useTransition hook]
    SD[StoryDetail] -->|performTransition| Hook
    TV[TerminalView] -->|performTransition| Hook
    Hook -->|validate| Runner[TransitionRunner]
    Hook -->|error state| SD
    Hook -->|error state| TV
    Runner --> Adapter[SupabaseAdapter]
    Adapter --> DB[(Supabase)]

    classDef deep fill:#ecfdf5,stroke:#34d399,stroke-width:3px;
    class Hook deep;

One hook owns the transition call, the error state, and the success side-effects. Callers get { performTransition, error } — a small interface.

Problem

The Transition flow spans four modules (App, transitionRunner, adapter, re-render) with handleTransition and handleReactivate in App.tsx acting as shallow shims that add error-toast wiring.

Solution

A useTransition(adapter) hook returns { performTransition, error, clearError }. Board and TerminalView call it directly. App.tsx drops two pass-through callbacks and one useState.

Wins

  • Locality: transition error state lives with the transition call
  • Leverage: one hook, two call sites (StoryDetail + TerminalView), zero pass-throughs
  • App.tsx loses ~25 lines of shallow wiring
  • Tests: transition error handling testable without mounting App

B. Pre-resolve StoryDetail cross-references; shrink the interface

Worth exploring in-process
src/components/StoryDetail.tsxsrc/components/Board.tsx

Before — wide interface, shallow implementation

Interface
story: Story allStories: Story[] blockers: Blocker[] dependencies: Dependency[] isAuthenticated: boolean onTransition: fn onClose: fn 7 props, 3 raw ref arrays
Impl
getDepStory() = allStories.find() × N

StoryDetail's interface is nearly as wide as its implementation. The getDepStory helper does linear searches at render time — complexity that belongs in the caller.

After — small interface, pre-resolved data

Interface
story: Story resolvedBlockers: ResolvedBlocker[] resolvedDeps: ResolvedDependency[] onTransition: fn onClose: fn 5 props, 0 raw ref arrays
Impl
Pure rendering — no traversal, no .find()

Cross-references resolved in useStoryDetail hook or at the Board level. StoryDetail becomes a pure render module.

Problem

StoryDetail receives raw reference arrays (allStories, blockers, dependencies) and performs linear lookups at render time to resolve blocker keys and dependency statuses. The interface is wide; the implementation is thin traversal.

Solution

Introduce ResolvedBlocker and ResolvedDependency types with story references already inlined. Resolve them in Board.tsx (or a useResolvedStory hook) before passing to StoryDetail.

Wins

  • Interface shrinks from 7 props to 5; raw arrays become resolved objects
  • Locality: cross-reference resolution lives where the data lives (Board, not Detail)
  • Tests: StoryDetail tests no longer need to construct matching allStories arrays with the right IDs
  • Leverage: if another view needs resolved blocker/dep data, the hook is already there

One interface with three methods. Two adapters (prod + test) justify the seam. The interface definition and both adapters can live in one file.

Problem

BoardDataAdapter (in lib/data.ts) and TransitionAdapter (in lib/transitions.ts) are separate interfaces, but the same concrete adapter always implements both. The split is a design artifact, not a real seam — there is no scenario where they vary independently.

Solution

Merge into a single BacklogAdapter interface with three methods: fetchAll, updateStoryStatus, onDataChange. Move both adapter implementations next to it.

Wins

  • One interface to understand, not two
  • Two adapters (Supabase + Memory) justify the seam
  • Deletion test: removing data.ts and transitions.ts interface types concentrates nothing in callers
  • TransitionAdapter is just Pick<BacklogAdapter, 'updateStoryStatus'> — a derived type, not its own module

D. Extract project-selection state machine into useProjectSelection

Worth exploring in-process

Before — state machine encoded across three locations

// App.tsx L16-24 getSavedProjectId() → localStorage
↓
// App.tsx L38-40 useState(() => getSavedProjectId())
↓
// App.tsx L47-57 useEffect: restore saved OR fallback to first guarded by `initialized` boolean
↓
// App.tsx L60-63 handleProjectChange → set + save to localStorage

The "which project?" question is answered by code scattered across 4 locations in App.tsx, guarded by a boolean flag. The deletion test: remove the initialized flag and the selection logic spreads even further.

After — one hook, one interface

useProjectSelection(projects)
→ selectedProject → selectProject(id) → filteredStories
Internals: localStorage restore, fallback, persistence on change. Zero callers see the `initialized` flag.

One module with a 3-method interface. localStorage read, initialization guard, and persistence are implementation details behind the seam.

Problem

Project selection logic spans three locations in App.tsx (localStorage read, useState initializer, useEffect with initialized guard) plus a separate handleProjectChange callback. The initialized boolean is a hand-rolled state machine that guards against repeated effect fires.

Solution

A useProjectSelection(projects) hook encapsulates all four concerns: restore from localStorage, fallback to first project, persist on change, and expose the filtered story list. App.tsx calls it once.

Wins

  • Locality: all project-selection logic in one module, not scattered across App.tsx
  • The initialized flag disappears behind the interface
  • Tests: selection logic testable without mounting App or localStorage mocks
  • App.tsx loses ~15 lines and one useEffect

E. Consolidate priority display into one source of truth

Speculative in-process
src/types.tssrc/index.csssrc/components/StoryCard.tsx

Before — two sources of truth

index.css
--color-priority-1: #F87171 --color-priority-2: #FB923C --color-priority-3: #FBBF24 --color-priority-4: #9CA3AF
↓ duplicated ↑
types.ts
PRIORITY_COLORS[1] = "var(--color-priority-1)" PRIORITY_BG[1] = "rgba(248,113,113,0.15)" resolvePriority(): PriorityDisplay

Adding Priority 5 means editing CSS variables AND TypeScript constants AND the Record<number, ...> type bounds. Three places, one concept.

After — CSS is the source; TypeScript references it

index.css
--priority-1: #F87171 --priority-1-bg: rgba(248,113,113,0.15) --priority-1-label: "Critical"
Components read colors via var() inline styles. PRIORITY_COLORS and PRIORITY_BG deleted. resolvePriority reads CSS custom properties at runtime.

One place to add a priority level. The CSS theme defines the value; TypeScript references it via getComputedStyle or inline var() references.

Problem

Priority colors live in two places: CSS theme variables in index.css and TypeScript constants in types.ts (PRIORITY_COLORS, PRIORITY_BG, resolvePriority). The resolvePriority function is a thin lookup — delete it and callers just inline var().

Solution

Define each priority as a CSS-driven data attribute or custom property set. Components read colors directly via var(--priority-${n}). Delete the three TypeScript lookup tables. Add a new priority by adding one CSS block.

Wins

  • Deletion test: removing PRIORITY_COLORS, PRIORITY_BG, and resolvePriority concentrates nothing in callers
  • One place to add a priority level (CSS only)
  • Components already use inline style= for priority colors — the TS constants are an unnecessary indirection

Top recommendation

Candidate A: Collapse the transition-error flow into a useTransition hook

This is the highest-leverage deepening available. The transition flow touches four modules today (App → TransitionRunner → Adapter → re-render), with App.tsx acting as a shallow pass-through shim that adds error-toast wiring. A useTransition hook puts the entire flow behind one small interface: { performTransition, error, clearError }. Two callers (StoryDetail, TerminalView) get the same capability without threading through App. App.tsx drops two callbacks and one useState. The seam already exists — the TransitionRunner is deep, the adapter is swappable — but the callers still route through a shallow orchestrator.

Start here. Candidates B and D (pre-resolved references, project-selection hook) are natural follow-ups that further shrink App.tsx. Candidate C (unified adapter) is the right long-term seam but can happen independently.
